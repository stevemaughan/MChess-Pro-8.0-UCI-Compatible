# UCI interface (as built)

What the engine (`zig-out/bin/mchess.exe`) does on the UCI protocol. The requirements are in AGENTS.md §10; this file describes what is built.

**`mchess` runs the joined engine (2026-11-19, task `uci`).** `src/main.zig` calls `uci.runJoined`: the original's own search on the ported routines (`src/engine.zig` on `src/engine_root.zig`), at the original's Fixed depth level, played as **normal play**: the original playing one side against moves entered at its command loop, with pondering off, as one copy of the program left running for the whole game (AGENTS.md §10.5). It began at about 55,000 nodes a second (Stage A, 2026-11-19; AGENTS.md, `docs/UCI_TIME.md` §6); since Stage B moved the units onto persistent structs it runs at about 2 million (2026-11-22: 1.6 to 1.8 million in three searches of 4 s, ReleaseFast, with other work on the machine). The stub engine (`uci_engine.StubEngine`, `uci.run`) remains for the shell's own unit tests.

Source: `src/uci.zig` (command loop, threads, options, position checks), `src/uci_parse.zig` (command parsing), `src/fen.zig` (FEN and move parsing), `src/uci_engine.zig` (the engine interface and the stub), `src/engine.zig` (the joined engine and the operator script), `src/uci_report.zig` (the `info` lines), `src/pipe_io.zig` (Windows pipes), `src/main.zig`. The threading and pipe handling are adapted from Cyrus IS Chess.

## Options

The values are stored by the shell and handed to the engine after each change. The joined engine uses `Hash` (below, "Hash"), `OwnBook`, `Book` and `Seed` (below, "Opening book"), `Use Tablebases` (below, "Tablebases") and `Move Overhead` (below, "go"). `Ponder` changes nothing (`go ponder` works either way). The class C corrections (AGENTS.md §9.2; DEV-001, DEV-050 and those of owner decisions 27, 28, 30, 31, 35 and 44) are always on (owner decision 25); DEV-054 is among them since 2026-11-22, in Black's form (decision 44), and DEV-062 has a switch that stays off (`pos.Fixes.parked`): there is no option to turn them off. Their switches stay in the code (`pos.Fixes`): `engine.OriginalEngine`, every correction off, is the engine the tests prove against the golden files, and `engine.Engine`, every correction on, is the one `mchess` runs. `setoption name Original Bugs …` is answered as an unknown option. Since 2026-11-20 (task integrate-fixes) every correction reaches the search (`docs/DEVIATIONS.md`, "Corrected on 20 November 2026"); the engine with every correction off is built as its own executable for matches, `zig build -Dfixes=false` → `zig-out/bin/mchess-original.exe`, and `tools/scripts/uci_protocol_test.py` checks the original's recorded moves and node counts against that build and only behaviour against `mchess`.

| Option | Type | Default | Meaning |
|---|---|---|---|
| `Hash` | spin 1–60 | 60 | The original's Settings / Hash-tables dialog (owner decision 24): N MB is N × 1,024 KB typed there, the total for its two main tables. The original halves it and uses the size at or below the half from its ladder, with that size's index mask and, at 15,360 and 30,720 KB, its 3/4 index mode (below, "Hash"). 60, the default, is the original's largest, two tables of 30,720 KB, which every golden file but `hash.jsonl` records. Larger sizes are not the original's logic and are not offered. |
| `OwnBook` | check | `false` | Whether the original's opening book is used (below, "Opening book"). **Off by default** (owner, 2026-11-19), unlike the original, which starts with its tournament book on (DEV-F, embedded files and the book's default). `false` is the original with its M-Chess book switched off (`DG:A5EE` = 1, the key K of the repeatable state): the engine exactly as before the book was joined, as every golden file but `book1.jsonl` was recorded. `true` is the original as shipped: the tournament book, learning and book learning off. |
| `Book` | combo `Tournament`, `Standard`, `Variety` | `Tournament` | Which of the original's three books (its Book menu's radio group, `docs/arch/40-opening-book.md` §6) `OwnBook` uses (owner decision 23). The three are three ways of drawing from the one file, `PRBOOK.M80`, which is embedded: `Tournament`, the original's default, `DG:A6A0` bit 5 (20h) set; `Standard`, bits 5 and 2 clear; `Variety`, bit 2 (4) set; the low byte copied to `DG:9EB6`, as the menu does. Read only by `book_probe`'s draw, so it changes nothing with `OwnBook` off. Case does not matter. |
| `Use Tablebases` | check | `true` | The original's Tablebases dialog's "Use tablebases" box (`DG:239C` bit 3; `docs/arch/41-tablebases.md` §5; owner decision 22). `true`: as shipped, 0Ah (below, "Tablebases"). `false`: 02h, the box unticked: the root never probes and every position is searched. The files stay embedded and bound. **Since 2026-11-22 (owner decision 44) `false` also frees the tablebase files unpacked at `uci`** (about 228 MB: private bytes 311 MB to 83 MB, the `setoption` taking under 10 ms), and nothing is unpacked while it holds, not by a `position`, a search or a second `uci`; **`true` again unpacks every file before the engine takes its next command** (about 0.15 s, on up to 8 threads), so a `readyok` after it comes when they are held and no move pays for them (below, "Tablebases"). **In an infinite search the tablebases are not used, whatever this option says**: `go infinite` (also with `ponder`), and a `go` with no limit, which searches as infinite does; the search is then the original's with the box unticked, and the setting is restored after it. |
| `Seed` | spin −1–65535 | −1 | The value `srand` is given where the original gives it the BIOS tick count (`0000:0109` at start-up). **The book's random generator (`DG:2DC8`) is seeded from `Seed` at the start of every game** (from the clock when it is −1): the first position after start-up, every `ucinewgame`, and every `position` that does not continue the game held (a rebuild, "The operator script"). It then runs on through the game. A `Seed`, `OwnBook` or `Book` set before the game's first search counts as set at its start; one set later takes effect at the next game's start (DEV-F13). −1 reads the clock as the original reads the BIOS tick count (ticks of 1/18.2 s since midnight, the low word); 0–65535 makes the book's choices reproducible: the same `Seed` and the same commands give the same book moves. A value out of range is refused with `info string error: bad value …` and the previous value is kept. Read only by the book's draw (with the Normal style the search draws no random number), so it changes nothing with `OwnBook` off. |
| `Ponder` | check | `false` | Announces pondering; `go ponder` works whatever its value. |
| `Move Overhead` | spin 0–5000 | 30 | Milliseconds for GUI latency, as Juggernaut's time control uses them (`docs/UCI_TIME.md` §2): subtracted from the target, twice from the clock in `panic` and `max`, and from `movetime`. 30 rather than Juggernaut's 10, chosen at Stage A, when a rebuild cost about 17 ms before the search and 1024 nodes about 20 ms. On 2026-11-22 a `go depth 1` on a rebuilt position took 0.7 ms (median of 30, `uci_latency.py`) and 1024 nodes take about 0.6 ms. It stays at 30 until it is measured after Stage B (owner decision 26). |

Option names are matched without regard to case. Check options take `true` or `false` (any case), spin options a decimal integer in range. Anything else prints `info string error: bad value '…' for option …`; an unknown name prints `info string error: unknown option '…'`. `Threads`, `MultiPV`, `UCI_ShowCurrLine`, `UCI_ShowRefutations`, `UCI_LimitStrength` and `UCI_Elo` are not declared (owner decision 17).

## Commands

| Command | Behaviour |
|---|---|
| `uci` | Identity, options, `uciok`. Since 2026-11-22 (owner decision 37) the first `uci` also unpacks every embedded tablebase file before it answers (below, "Tablebases"): `uciok` comes about 0.2 s after `uci` (ReleaseFast and ReleaseSafe, 8 threads), and no input is read meanwhile. A second `uci` unpacks nothing, and no `uci` unpacks anything while `Use Tablebases` is false (owner decision 44). |
| `isready` | `readyok`: at once while a search is running that has not been told to stop, otherwise after the commands before it; never before what a command sent before it prints (below, "Threads"). |
| `ucinewgame` | The held game is dropped; the start position follows (a rebuild, below). Clears a rejected position. |
| `position startpos \| fen <FEN> [moves …]` | Sets the position (below). |
| `go …` | Searches (below). Exactly one `bestmove` per `go`. |
| `stop` | Ends the running search, or a `go` still queued; its `bestmove` follows. Ignored when idle. |
| `ponderhit` | The pondered move was played: a `go ponder` now ends as a normal search. |
| `setoption name <id> [value <x>]` | Sets an option (above). |
| `debug on \| off` | Accepted; it changes nothing yet. |
| `quit` | Stops any running search (its `bestmove` is still printed), drops queued commands, exits with status 0. A `go` still queued and not started when `quit` arrives is dropped with them. |
| anything else | Ignored, as UCI requires. A known command that cannot be parsed (`debug x`, `setoption` without `name`) prints `info string error: …`. |

The end of input acts like `quit` except that queued commands still run, so every `go` piped in gets its `bestmove` (each such search is stopped, so it ends at its first stop check).

Lines may end in LF or CRLF, words may be separated by spaces or tabs, and a UTF-8 byte-order mark before the first command is skipped. A line longer than 64 KiB prints `info string error: input line too long, ignored` and is skipped. User text quoted in an error message is cut to 80 bytes.

### Threads

The main thread only reads standard input and never waits for the engine. `setoption`, `ucinewgame`, `position` and `go` run in order on one worker thread, which owns the engine; a `go` runs to its end before the next of them, so a script may send `go depth 5` and the next `position` at once. A `go infinite` or `go ponder` is stopped by any later one of these commands, since a GUI that sends one has abandoned that search.

`isready` is answered by the input thread at once when a search is running that has not been told to stop and nothing is queued behind it but other `go`s not told to stop (a GUI sees a queued `go` as a search under way). Otherwise it joins the worker's queue behind every command it must not overtake, and is answered when the worker reaches it: so `readyok` never comes before a queued `position`'s rejection, a `setoption`'s or `ucinewgame`'s effect, or the `bestmove` of a search that was told to stop (by `stop`, or by a later command ending a held `go`) or had ended. It waits for a running search only when a command sent before it is queued behind that search. It never stops a search itself. (Before 2026-11-22 it was answered at once whenever a `go` was running or queued, including a search that had been told to stop and had just printed its `bestmove`: in 7 and 24 runs of 500 of the protocol test's session "rejected positions" on a loaded machine, `readyok` came before the rejection of a `position` sent after that `bestmove`; after the change, none in 500. The session "readyok after what came before it" hammers that moment: every one of 500 runs failed before, none after.)

The input thread sets two atomic flags, `stop` and `ponderhit`. The search reads `stop` (below, "Stop"); `ponderhit` is read only by the shell, which holds `bestmove`. Output lines from both threads go through one mutex and are written and flushed one at a time. On Windows, pipes are read and written with overlapped I/O, which works whether the GUI's pipe is synchronous or overlapped (fastchess uses overlapped pipes).

## Positions

The shell checks a `position` command in this order, and the first failure rejects it:

1. **Syntax of the command**: `startpos` or `fen`, then optionally `moves` and the moves.
2. **The FEN** (`fen.parse`): exactly 8 ranks of 8 squares; piece letters `PNBRQKpnbrqk`; side `w` or `b`; castling `-` or the letters `KQkq` in any order, each at most once (no Shredder or X-FEN letters); en passant `-` or a square on the 6th rank (White to move) or 3rd (Black to move); then the halfmove clock and fullmove number, decimal 0–65535. **Only the placement is required** (owner decision 16, 2026-11-19, as his engine Juggernaut reads a FEN): some GUIs, Shredder among them, send a FEN without its last fields, so any field after the placement may be missing, together with all that follow it. A missing field takes its default: White to move, no castling rights, no en-passant square, halfmove clock 0, move number 1. A field that is present must be well formed; the side letter is taken in either case. Six fields at most.
3. **Consistency** (`fen.checkConsistency`): one king per side; no pawn on the 1st or 8th rank; at most 16 pieces and 8 pawns per side; each castling right has its king and rook on their original squares; an en-passant square has the pawn that made the double step in front of it and is empty, as is the square behind it; if the side to move is in check, some single move of the other side can be taken back so that, before it, the side to move was not in check (any move of chess: a piece's move or capture, a pawn's step, double step, capture or promotion, en passant, castling not out of or through check; with an en-passant square, that double step). A check no legal move could have given, such as two pawns' check, a pawn and a knight, two knights or three checkers, is refused as `the side to move is in check in a way no legal move could have given` (decision 38, DEV-064: no game reaches such a position, and the original's search crashed on two pawns' check, `docs/ROBUSTNESS.md`, fault 1).
4. **The moves' syntax** (`fen.parseMove`): lower-case long algebraic, `e2e4`, `e7e8q`; a promotion letter (`n b r q`) only on a move from the 7th rank to the 8th or the 2nd to the 1st, to the same or an adjacent file; `0000` is not accepted. As many moves as the 64 KiB input line holds (owner decision 29): about 13,100 from the start position. A longer line is reported as too long and ignored.
5. **The engine** (`Engine.setPosition`): Setup mode's test of a FEN's board (below) and the legality of each move by the original's own code (the move generator and the king test on the auto-play path, `check_entered_move` 38C0:5864 on the normal-play path). The generator is the one the original uses at that position (`src/legality.zig`, DEV-066): `gen_evasions` when the game record's check byte for the position is set (the byte main reads at 0000:0693), as the original's root and `check_entered_move` choose, so every legal reply to check is accepted; otherwise `gen_all_moves`, whose list keeps 100 moves, so that outside check, at a position with more than 100 pseudo-legal moves, a legal move past them is refused (`move N: not a move of the original's move generator`), as the original's own move entry refuses it (kept by the owner, decision 41). **A promotion needs its letter, and any other move takes none** (DEV-F22): a pawn's move to its last rank without `n`, `b`, `r` or `q` is refused as `move N: a promotion needs n, b, r or q`, a letter on a move that is not a promotion as `move N: a piece letter on a move that is not a promotion`, on the continuation path as on the rebuild. The letter stands for the key pressed at the original's promotion prompt (38C0:30CB), which takes no other key and has no default. **There is no limit on the length of a game** (owner decision 26, DEV-F19). The original ends a game when its move number reaches 202 (38C0:1974), the 402nd ply: its game record holds move numbers 0–202 a side. The engine plays on: from game ply 300, between turns, it drops the oldest plies of the record and renumbers every game ply and move number, never below ply 202, so that every test the original makes on the absolute ply or move number gives the same answer (`src/gameslide.zig`; `docs/arch/34-game-move-path.md`, "Playing on past move 201: the slide"). Up to ply 401 every search is the original's, slid or not. A long `position` is rebuilt by replaying its moves, sliding as it goes, in time linear in its length (about 50 µs a ply in ReleaseFast at Stage A: 4,000 plies in 0.2 s; on 2026-11-22, 4,000 plies of knights moving to and fro were rebuilt and searched to depth 1 in 5 to 6 ms, 1,000 in 1.2 ms); a `position` that adds the opponent's move to the game held is continued, however long the game. The only limit is the length of the input line, 64 KiB, which holds about 13,100 moves (owner decision 29).

A rejection prints `info string error: position rejected: <reason>`, for example `… rejected: move 3 'e2e9': move has a square that is not a1..h8` or `… rejected: move 7: not a move of the original's move generator`. Until the next accepted `position` or a `ucinewgame`, every `go` prints the same line again and `bestmove 0000` (held, like any `go`, while `infinite` or `ponder` requires it). The engine is never searched on a rejected position, and the shell never substitutes another one.

Before any `position` command the position is the start position.

### position fen

`position fen` takes the original's Setup mode route (`src/adapt_setup.zig`; `docs/arch/23-position-setup.md`, "From the command loop to the first search after a set-up"): from the command loop after start-up, the board and the side to move are entered as Setup mode takes them; then the operator script below. Even the start position's FEN takes this route, and searches differently from `startpos` (the knights' slots, the book flag, the move number), as the original does.

- **Refusals.** A board Setup mode refuses is rejected with its message: `position rejected: the original's Setup mode refuses it: NO WHITE KING` (also `Too many WHITE KINGS`, `NO BLACK KING`, `Too many BLACK KINGS`, `Too many WHITE PAWNS`, `Too many WHITE PIECES`, `Too many BLACK PAWNS`, `Too many BLACK PIECE` (sic), `WHITE IS IN CHECK`, `BLACK IS IN CHECK`; the last two are the side not to move in check, or kings side by side). The shell's own checks (above, step 3) come first.
- **Fields Setup mode cannot give** (`docs/arch/23-position-setup.md`, table "What Setup mode can express of a FEN"):
  - *Castling*: Setup mode gives the rights the board allows (king on its e-square, rook on its corner). A FEN that withholds one of those has it stamped lost after the build, as the original's position loader (`0EF8:6AAB`) does, without a new hash key (the loader's suspected bug 2; read, not run). A FEN cannot give a right the board does not allow (the shell rejects it). Owner decision 15 (DEV-F06): such a FEN is accepted and the engine never proposes a castling move its rights do not give. A FEN without its castling field has no rights (owner decision 16).
  - *En passant*: Setup mode writes none. A FEN's square is taken as the loader takes it (`0EF8:6AA3`, into `[90B8]` before the build).
  - *Halfmove clock and fullmove number*: no route of the original takes them: the set-up position is move 1 with the irreversible-move count afresh. They are not used.
  - Each `go` on such a position prints what was done with each, as `info string position fen: …` lines.

## The operator script

How UCI commands map onto the original's own operations (AGENTS.md §10.5). The engine holds one game: its start (`startpos`, or a FEN through Setup mode), the moves played in it, and where the original stands in it (`engine.Phase`: at main `0000:0526` ready to search, or at its command loop waiting for the opponent's move after its own).

**Start-up** (once, `Engine.init`): the original's start as far as it writes engine state, to its command loop with White to move (`EngineRoot.startUp`: the C start-up's image, hash_setup with 64,512 KB of XMS, new_game_position, the shipped settings files, main to the command loop, then the menu choices of the repeatable state, AGENTS.md §5: book ignored, learning and book learning off, Fixed depth 4). Every game starts from this image (`loop_image`). With `OwnBook` on, the image has the M-Chess book on (`DG:A5EE` = 0, as the shipped `UBOOKS.M80` gives it). At each rebuild, whatever `OwnBook` says, the random seed `DG:2DC8` is `srand(Seed)` (start-up's `0000:0109`), and again at each `setoption` that comes before the game's first `go` (`Engine.game_fresh`), so that the shell's own rebuild at start-up, made before the GUI sends its options, and a `Seed`, `OwnBook` or `Book` sent between `position` and the first `go`, give the draw the options ask for (DEV-F13). Until 2026-11-22 the seed was written only at a rebuild with the book already on, so the first game after start-up drew from the start-up value 17 whatever `Seed` said, until a `ucinewgame`.

**`position` that continues the held game** — the same start, the held moves (which end with the program's own move, played by its last search's conclusion) and exactly one more move: that move is the opponent's, and it is **entered as in normal play with pondering off** (`EngineRoot.enterMove`: the squares into `9360`/`9361`, `check_entered_move` 38C0:5864, the promotion piece (the move's letter, which must be there exactly when `check_entered_move`'s board test makes it a promotion; if it does not agree, the position is rebuilt instead, and the rebuild refuses it with the reason, DEV-F22), `play_entered_move` 38C0:554E, the evasion count, the game board, `check_new_control`, the command loop's exit, main to 0526; `docs/arch/34-game-move-path.md`, "Normal play: the turn with pondering off"). Nothing else is touched: the main hash tables (kept or cleared by main's own test before the search, `33-` step 9), the killers, the evaluation's tables, the reply list of `set_predicted_reply`, the game record and the score history are what the original would have.

**Any other `position`** (a new game, a different line, a take-back, a `position` with no new move or several, the same position for a second `go`, a FEN, `ucinewgame`) **rebuilds** the game (`Engine.rebuild`): the command loop after start-up; for a FEN, Setup mode; the key `!` (pondering off, `EngineRoot.togglePondering`, as the oracle's normal play types it); then

- *no moves*: the program takes the side to move (Ctrl-A, 38C0:3F1C, `EngineRoot.autoPlay`: `[8DDE]` = the side to move, its clock, main to 0526), and auto-play is then switched off (`[9FCF]` = 0) so that its move is played as in normal play. `[9FCF]` is read before a search only at the timed levels and by displays (rootprep `0000:0465`, `140A`), so the search is the auto-play search the golden corpora prove (smoke, corpus2);
- *one move*: it is entered as the opponent's move, as above, and the program plays the other side. This is exactly how the oracle's normal-play scenarios start (`normal1.jsonl`: `np-open-black-d4` from the start, the FEN scenarios with the opponent to move);
- *two or more moves*: the program plays every move as its own in auto-play (Ctrl-A, then for each move `play_best_move` 38C0:01E0 and the turn, `EngineRoot.nextTurnAutoPlay`: the path of the golden corpora), then auto-play is switched off for the search.

After *no moves* and *two or more*, the program's taking of the side to move ends as the original's does with auto-play off (38C0:3FE6–3FEF: `sub_38C0_1176`, `[AE44]` = `[717C]`, the opponent's side; Ctrl-A skips it, since it sets `[9FCF]` = 1 at 3F24). Before 2026-11-19 (task options) this was missing: `[AE44]` kept start-up's 0, and when the program was White the opponent's next move failed `enterMove`'s test at 38C0:50DB (taken for monitor mode), so the next position was rebuilt instead of continued (`docs/OPEN_QUESTIONS.md` question 19). No search reads `[AE44]` (every reader has a zero search count in the profile). Tested: after a rebuild of 0, 1, 2, 3 and 6 plies, the next position with the opponent's reply is continued (`src/engine_uci_test.zig`).

**What the original would have done in place of a rebuild.** For a new game: the New game command (Ctrl-N, `EngineRoot.newGameCommand`). It is ported and proved up to main 0526, but not the search that follows (`EngineRoot.mainAfterNewGame` is read only: the emulator asks for the CD-ROM there, `docs/OPEN_QUESTIONS.md` question 10), and it keeps state of the last game (the killers, the last played ply `[A36A]`, the main hash tables until main's own clear) that a GUI's new game would make depend on what was played before. The engine starts every game from the start-up image instead, which is what the original does at its first game. For a take-back: `take_back_ply` (38C0:3DDD, ported in `gamemove.zig`) and the take-back of several plies (`38C0:16C2`, not ported). For a position reached by a different line, or a game joined in the middle: the original would have had the moves typed in monitor mode (`38C0:50E1`, not ported) or replayed. In each case the rebuild gives the position the original would reach, but not its carried state (the hash tables are empty, the killers and the evaluation tables are those of the auto-play replay, which searches nothing). These are decisions for the owner (below).

**`go`**: the program searches the side to move at its Fixed depth level (`[A274]` = 3, `[1E02]` = the depth; main from 0526, `EngineRoot.search`). Then, as the original does at once, it plays its move: main's conclusion and `play_best_move(0)` with `set_predicted_reply` (`EngineRoot.playMove`), and main on to its command loop (`EngineRoot.toOpponentMove`: the ponder test, pondering off). The held game now ends with the program's move, waiting for the opponent's. The ponder move printed with `bestmove` is `set_predicted_reply`'s reply (`DG:8FDE`), which it has checked legal.

**A book move** (`OwnBook` on): main's `book_probe(1, side)` (`0000:070F`) hands over a move; main copies it to `[A36C]` and plays it with `play_best_move(1)` (`0000:06EF`, `EngineRoot.playBestMoveFromMain`), with no search, and goes on to its command loop (`EngineRoot.toOpponentMove`) as after a search; the held game ends with the book move. The book is also probed in mode 2 after the program's moves (`play_best_move`'s end, `38C0:0C58`), which keeps the book-exit ply `[9FBC]` at 0 while the game is in the book. No ponder move is printed after a book move (`play_best_move(1)` clears the prediction).

`go` for either side at any time works: a `position` that is not a continuation is rebuilt with the program on the side to move.

**Proved** (`src/engine_uci_test.zig`): five games of `tests/golden/normal1.jsonl`, 58 searches, replayed command by command as a GUI sends them (`position startpos|fen … moves …` growing by two plies, `go depth N`), each equal to the original on the move, node entries, makes and line hash, every search after the first reached by continuing the held game: `np-open-black-d4` (the program Black from `startpos`, depth 4, 10 searches), `np-open-white-d3` (White from a FEN, Black to move, depth 3, 14), `np-checks-white-d3` (White from a FEN, 8), `np-middle-white-d4` (White from a FEN, 12), `np-ending-black-d5` (Black from a FEN, 12). Not replayed: `np-middle-black-d5`, whose first twelve moves the oracle typed before the program took a side (the operator script has no counterpart). The oracle's FENs are entered with the rights Setup mode gives the board; the headers' FENs stop before the castling field. The engine of the tests has every class C correction off (`engine.OriginalEngine`), as the golden files record the original.

## go

Every parameter is parsed: `searchmoves ponder wtime btime winc binc movestogo depth nodes mate movetime infinite`, in any order, each at most once. A negative number (a flagged clock) counts as 0. An unknown or repeated parameter, or a parameter without a valid number, prints `info string error: … in '<line>'` and `bestmove 0000`. A `searchmoves` move that is not a well-formed move prints `info string error: searchmoves '…': …` and `bestmove 0000`.

**Time management is Juggernaut's** (owner decision 20; the design is `docs/UCI_TIME.md`; task time-join, 2026-11-19). Every `go` but `go depth N` runs the original's Fixed depth level at depth 30 (`[A274]` = 3, `[1E02]` = 30), the level the golden files prove, and Juggernaut's time control (`src/timecontrol.zig`, one for the engine's lifetime, so that its iteration history carries over as in Juggernaut) decides when to stop. None of the original's own time management runs (its budget, `timebudget.zig`, is not called). The time control reads the search through the observer (`engine_root.Observer`, `src/uci_report.zig`) and writes nothing the search reads but the two stops below.

| `go` | Search, and when it stops |
|---|---|
| `depth N` | Fixed depth N (1 to 30), as before. |
| `wtime`/`btime` (with or without `winc`, `binc`, `movestogo`) | Depth 30 with Juggernaut's budget (`target`, `panic`, `max`, `docs/UCI_TIME.md` §2, Move Overhead included; since 2026-11-22 `panic` and `max` are at most four fifths of the mover's clock, and never its last Move Overhead): inside an iteration at the first 1024-node test (or the loop's first node entry) at or past `panic` (`max` while the root is in trouble); at the end of an iteration by Juggernaut's rule (§3.2: the branching estimate against 2.1 × target × the scaling factor). |
| a clock and `depth N` | Both: whichever comes first. |
| `movetime N` | Inside an iteration at `N − overhead`; at the end of an iteration at `N`. |
| `nodes N` | At node entry N, tested at every node (not at the 1024-node test), so that the same N always gives the same search; the nodes the unwinding then enters are counted (0 to 5 past N measured). |
| `mate N` | At the end of the first iteration whose score is a mate in N moves or fewer (the `score mate` arithmetic below, "Mate scores"); depth 30 otherwise. |
| `infinite` | Depth 30, held until `stop`; the original's mate stop may end the search earlier, and `bestmove` is still held. The tablebases are not used (owner decision 22; above, `Use Tablebases`). |
| no limit | As `infinite`, but `bestmove` is not held: a search to depth 30, which in practice `stop` ends. The tablebases are not used. |
| `ponder` | As the other limits say, except that no time rule stops the search before `ponderhit` (a `depth` or `nodes` limit does); after `ponderhit` the clock rules apply at once, with the time pondered counted as spent (elapsed time runs from the `go`). The shell holds `bestmove` until `ponderhit` or `stop`. |
| `searchmoves` | Not supported: `info string searchmoves is not supported (the original's excluded-move list is not joined): every move is searched`. |

**The clock.** Elapsed time runs from the moment the input thread read the `go` line (`std.Io.Clock.awake`, stamped in `uci.Worker.push`), so the rebuild of a position and main's root preparation are counted. The same clock gives `info time` and `nps`.

**What the time control is handed** (`docs/UCI_TIME.md` §4), by the observer:

| Input | Where it comes from |
|---|---|
| iteration, score, best move | at the end of each iteration (the loop's `root_search` returns at `0000:15FA` with a score above the window's bottom, or at `165D`): the iteration depth `[744E]`, `root_search`'s result, `[A36C]` |
| nodes | node entries of this search so far (`EngineRoot.live_nodes`, the count `info nodes` gives, current at every entry) |
| legal root moves | `[A518]` (`RootState.legal_count`) |
| the opponent's last move's target square | the last move of the `position` command |
| root re-searches in the iteration | each fail high re-searched (`show_score` from `0000:2835`, after which root_search searches the same move again at `287E`), and the first root move failing low (the loop's `root_search` at `15FA` returns at or below the window's bottom, and the loop re-searches it at `165D`) |
| root trouble | read at each 1024-node test: an iteration of this search has completed, a root move of the current iteration has an exact score (the last new best shown at `0000:2C1F`, which is also where a failed fail-high re-search restores the earlier best), and that score is more than 50 below the completed iteration's. A fail high's lower bound and the first move's fail low are not scores yet, as in Juggernaut, whose root move sets `RootTrouble` only once its re-searches are resolved |
| the expected move | the third move of the previous search's PV (`DG:93B0`, read before the move is played) when the position continues the held game (the operator script's continuation, not a rebuild) and the opponent played the PV's second move; none otherwise |
| pondering | `go ponder` until `Signals.ponderhit` |

**How a stop is carried out**, both proved by `src/engine_time_test.zig`:

- **Inside an iteration** the stop flag `[A4FA]` is written exactly as for `stop` (below, "Stop"); the search unwinds through the original's code and plays `[A36C]`, the best root move so far. The time control is consulted every 1024th node entry *of this search* (`EngineRoot.live_nodes`), so a scripted clock stops a search at the same node whatever the engine searched before, and also at the iteration loop's first node entry (`EngineRoot.loop_entries`), so that a clock already past `panic` when the search begins costs only main's preparation and not 1024 more nodes: without that test, 2+0.02 self-play lost one game in 200 on time (every move of a long ending cost about 33 ms against a 20 ms increment). `stop` is read every 1024th entry of the engine's own count, as before.
- **At the end of an iteration** the loop's depth limit `DG:64` is lowered to that iteration's depth + 1 (`engine_root` `LoopEnv`, the loop's `root_search` case). `DG:64` is written only by main before the loop (rootprep: 35, or the Fixed depth + 1) and read only at the loop's top (`0000:146F`). The loop then does what it does after every iteration (the depth step, the mate stop, the re-sort of the root list) and ends at its top exactly as the Fixed depth search of that depth ends. **So a timed search the time control ends after iteration k is `go depth k`**: the same move, node entries, makes, line hash, and the image after the move equal byte for byte but `[1E02]` (30 against k), which main rewrites before every search. It costs no node, and the last `info` line (the iteration's) has the `bestmove` as its first PV move.
- Before any root move has a score (a clock so short that `panic` has passed at the first test): the first move of the root list, as for `stop`.

**Measured** (`tools/scripts/uci_protocol_test.py`, session "time controls", ReleaseFast, timed from the `go` line to the `bestmove` line by the script): 18 clock searches from 200 ms to 60 s on three positions, each `bestmove` within `max` + overhead + 0.15 s; the largest share of the mover's clock used was 0.297 (10 s with `movestogo 5`: 2.97 s against a `panic` of 2.955 s), and the largest time beyond `max` 16 ms (200 ms on the clock, `max` 4 ms: the rebuild and main's preparation); `movetime` 100, 300 and 1000 within the time; `go nodes 5000` twice equal; `go ponder` with a clock not ended in 1 s, and `bestmove` within 0.15 s of `ponderhit`. On 2026-11-22 the same session gave a largest share of 0.299 and a largest time beyond `max` of 31 ms.

**Safety run** (step 5 of `docs/UCI_TIME.md` §7; the first run, 2026-11-19): `cutechess-cli` 1.x, `mchess` (ReleaseFast) against itself, openings from `UHO.pgn` (random, 8 plies), 6 games at a time on a 16-thread machine, games over 150 moves adjudicated drawn. **2+0.02, 200 games: no time loss, no illegal move, no crash or stall**; the most a move used was 0.153 of the clock it had, and the least time left after a move 0.389 s. **5+0.05, 200 games: no time loss, no illegal move, no crash**; at most 0.272 of the clock, least time left 0.305 s. (A first 2+0.02 run, before the time control was also consulted at the loop's first node entry, lost one game in 200 on time; above.) cutechess warned of an illegal move inside a `pv` about 140 times in 200 games (deep in the line; the `bestmove` was always legal): the PV was then cut only by the checks of `uci_report.writePv`, not by a full legality test (AGENTS.md §9.3). Now it is (below, "Illegal moves in the PV"): **2+0.02, 100 games** (task options, same settings, 7 at a time): no illegal-move warning of any kind, no time loss, no crash; 92 decisive by mate, 8 drawn (repetition, material, fifty moves). **Since then** (2026-11-20 to 22), 12,980 more games, from half a second for the game to 3+2 and 40 moves in 60 s, pondering on and off, most with the ReleaseSafe build: two faults found and fixed (a crash at iteration 30, time losses at one second for the game), and after them no crash or illegal move and one time loss, at 40 moves in 60 s on the last move before the control (`docs/UCI_TIME.md` §6).

`bestmove` is held as UCI requires: after `go infinite` until `stop`; after `go ponder` until `ponderhit` or `stop` (a `go ponder infinite` until `stop`). The shell, not the engine, prints `bestmove`, so there is exactly one per `go`. The move is always a move of the original's root list (the search's `[A36C]`); with no move (the game is over in the position) `bestmove 0000` with `info string no move: the game is over in this position`.

### Stop

Owner decision (2026-11-19): not the original's keyboard poll. **Every 1024th node entry of the iteration loop reads `Signals.stop`**, and if it is set writes the original's stop flag `[A4FA]` = 1, once: the value of the original's own time-out (`2EC8:2F3E`; `searchnode.timeTestD`). The count is kept by the node interface the root gives the search (`engine_root.EngineRoot.StopCtx`, which is the node's own interface with the count added; `node_tick`), counting both the root's node calls and every child entry. The search then ends through ported code: the node tests `[A4FA]` after a move is searched and unmade (`0000:41CB`, `4DB0`) and unwinds; root_search returns at `0000:26C5` with the best move so far (`[A36C]`; with a fail-high re-search pending at a later move, `0000:8FE6` keeps it); the iteration loop concludes (`1605`, `166E`); main plays `[A36C]` (stop 1: `play_best_move` plays). The timer tick, the poll requests `[75B6]` and the poll routine `1E9D:7514` are not used: `[75B6]` stays 0 and the poll bindings do nothing.

- The check is armed only in the iteration loop (`EngineRoot.iterate`). The pre-scoring of the root moves in main (`0000:09A6`–`0FC8`, `[724D]` = 1) is never interrupted: there the original parks a key as stop + 10 (`1E9D:7128`) and, after pre-scoring, sets `[A4FA]` from it (`1063`, `rootprep.zig` line "stop + 10 parked") and concludes at `131E` without a search (UNVERIFIED, never recorded). Pre-scoring is one node per root move; a stop that arrives during it is seen at the loop's first 1024th node.
- **A stop before any root move has a score** (in iteration 1, before the first root move's tree returns): root_search has set `[A36C]` to the first move of the root list (`0000:22C0`: `best_move = root_moves[0]`), which pre-scoring has sorted first; it is played. It is a legal move (the root list holds only the legal moves, `[A518]`). The final `info` line then has no score (below).
- A search that is not stopped makes exactly the same tree: the count only reads the flag; every golden search passes through `StopCtx` (all of `zig build test`).
- Measured (`tools/scripts/uci_latency.py`, ReleaseFast, this machine, 30 rounds): `stop` to `bestmove` under `go infinite` after 0.3 s of search, median 16 ms, max 28 ms. `go depth 1` to `bestmove`, median 17 ms (most of it the rebuild: two 30 MB tables cleared). `ponderhit` to `bestmove` after a finished `go ponder depth 1`, median 0.15 ms. Again on 2026-11-22 (ReleaseFast, 30 rounds, other work on the machine): `stop` under `go infinite`, median 2.2 ms, max 4.8 ms; `go depth 1`, median 0.7 ms, max 1.9 ms; `ponderhit`, median 0.16 ms.

## Feedback

Owner requirement (AGENTS.md §10.6, decision 17). All of it is gathered by observing the root (`engine_root.Observer`, `src/uci_report.zig`) and is never read by the search: the observer is told of the root's callee calls and of the iteration loop's `root_search` returns; it writes nothing the search reads. Proved: the five normal-play games are equal to the original with reporting on, and `np-open-white-d3` gives the same nodes, makes and line hash with reporting off and on (`src/engine_uci_test.zig`); every other golden test runs with no observer through the same `StopCtx`.

**When lines are printed:**

| Line | When (the original's own point) |
|---|---|
| `info depth d seldepth s score … nodes … nps … time … hashfull … pv …` | at each new best root move: the call of `show_score` (38C0:9BEA) from root_search at `0000:2C1F`, where the original shows the new score on its thinking display (also after a failed fail-high re-search, the earlier best restored, line 480 of `rootsearch.zig`) |
| the same with `lowerbound`, pv = the move | at each root fail high: `show_score` from `0000:2835`; the score is the window's top |
| the same | at the end of each iteration: the loop's `root_search` returns at `0000:15FA` or `165D` with a score above the window's bottom |
| the same with `upperbound` | the iteration's first root move failed low (`root_search` returned at or below the window's bottom, `0000:2CA3`); the loop re-searches below it |
| `info depth d currmove m currmovenumber n` | at each root move made (make_move from root_search, `0000:24BC`; the original shows the move it considers at `253E` just after), once the search has run one second |
| a final line | before `bestmove`, unless the last line already holds the final node count |

`show_score` is called whenever the search is not pondering, whatever the display settings, so these lines do not depend on the original's display options. A search stopped part-way through an iteration prints no iteration line; the final line gives the last score reported.

**Where each value comes from:**

| Value | Source |
|---|---|
| `depth` | the iteration depth `[744E]` (`RootState.depth`) at the line's point; in the final line, the depth of the last score reported |
| `seldepth` | the deepest ply a node of this search was entered at (`EngineRoot.max_ply`, from the node entries, which give their ply), less 1: the root's moves are made at ply 2, so a node at ply p is p − 1 plies below the root; at least `depth` |
| `score cp` | the root score in the side to move's view (`show_score`'s argument, `[934E]` after a new best, or `root_search`'s result) **halved, truncated toward zero**, as the original's display shows it (DEV-F23). The evaluation counts a pawn as 200 (the piece values at `DG:1498`: P 200, N 650, B 700, R 1100, Q 2000; the Custom style doubles values entered in centipawns, `0000:E752`–`E757`), and the display takes the sign, halves the magnitude and prints it in pawns: the default display `38C0:9A2E` (`9B5F`–`9B6C` the sign, `9B89 sar word [bp+6],1`), and show_score's numeric path `38C0:9BEA` (`9DB6`–`9DC0`, `9E10`–`9E13`). So a raw 103 is sent as `cp 51` (the original shows +0.51) and −103 as `cp -51`. The search, the time control and every test against the golden files use the raw score |
| `score mate N` | below |
| `lowerbound` / `upperbound` | a fail high at the root (the score is the window's top, `hi`), or an iteration that returned at or below its window's bottom (`lo`) |
| `nodes` | node entries of this search as the oracle counts them (`EngineRoot.nodes`: the root's node calls and every node entry below them, from pre-scoring on; the golden files' `nodes`) |
| `time`, `nps` | a monotonic clock (`std.Io.Clock.awake`) from the start of the `go`, read only for reporting; `nps` = nodes × 1000 / ms |
| `hashfull` | a sample: the used slots (bound bits, byte 8 & C0h, set) among the first 500 slots of each of the two main tables, in permille |
| `pv` | the PV row of ply 1 `DG:93B0` (`RootState.pv`, length `[B42B]`) when its first move is the best move `[A36C]`, else the best move alone; for a fail-high line the move being searched. The words hold from and to (bit 7 of each a flag) but no promotion piece: the first move's piece is `[A36C+2]`'s, a later promotion is shown as a queen. The line is cut before its first move that is not legal (AGENTS.md §9.3 item 4; below, "Illegal moves in the PV") |
| `currmove`, `currmovenumber` | the root move made, `root_moves[i]` (`DG:3BC4`), and its 1-based number `[8CBC]` |

**Mate scores.** A node at ply p (the root's moves are made at ply 2) whose side to move is checkmated returns p − 20000 (`self.ply -% 0x4E20` in `searchnode.zig`: `0000:41C2` and its pair in the Black node; at ply 2 in root_move_search −20000, DEV-036), and the score is negated up the tree. So a root score s with |s| > 19700 is a mate at ply p = 20000 − |s|, as the original's display has it (`38C0:9A7C cmp si, 4CF4h; jle` and `9AC2 cmp si, B30Ch; jge`: a mate above 19700 and below −19700; `root_search`'s own test for a won score, `0000:2C77`, is `si >= 19700`, and no evaluation reaches 19700 either way), p − 1 plies after the root. A mate given by the engine is at an odd number of plies after the root, one suffered at an even number; in both cases the mating side's moves are N = p / 2 (integer division), at least 1: `score mate N` for s > 0, `score mate -N` for s < 0. A mate in one gives 19998 (or 20000 from root_move_search's ply-2 mate); being mated in one, −19997. Tested (`src/engine_uci_test.zig`, `tools/scripts/uci_protocol_test.py`): mate in 1, 2 and 3 with White and with Black to move, mated in 1 and 2 with either side to move, each `score mate N` exact on the final line.

Where the distance is not exact, the line still shows what the original's score says:

- **Scores from the hash tables are not adjusted by ply** (the slot holds the score as it was stored, `searchnode.zig` probe, `0000:2F8x`; the original stores and reads it without a ply correction). A mate score found through a transposition at another ply gives a distance off by the difference. The engine prints N from the score as it stands; it can be longer or shorter than the true distance in such a line.
- **A mate at ply 2 in root_move_search counts only if a check extension was made**; otherwise it is scored 0 (DEV-035). A mate in one can then show as `score cp 0` at depth 2 or more, until another line finds it.
- **The Mate in N and Shortest mate levels** (`[1E08]`) are not joined; `go mate` searches at the Fixed depth level (above).
- **Tablebase moves** (below, "Tablebases"): a move the root plays from the tablebases without a search is reported as `info depth 1 seldepth 1 score … nodes 0 nps 0 time … hashfull … pv <move>` and `info string tablebase move: the original's root played it from its tablebases without a search (N probes accepted)`. The score is the root's tablebase score of the move (`[A8DA]`, set at `0000:0FB8`): a win in m moves after it is 20000 − 2m, so `score mate m+1`, exact (the tablebases count every move); a loss `score mate -N`; a draw `score cp 0`. If a move is played without a search for another reason (main's other no-search exits), the final line is `info depth 0 nodes … time … pv <move>`, with no score, and `info string the original played this move without a search (…)`.
- **A search stopped before any root move was scored** prints `info depth 1 seldepth … nodes … time … pv <move>` with no score, and `info string stopped before the first root move was scored: the first move of the root list, no score`.

Not printed: `currline`, `refutation` (owner decision 17), `multipv`, `cpuload`, `tbhits`, `sbhits`.

**Illegal moves in the PV** (AGENTS.md §9.3 item 4; task options, 2026-11-19). The PV is the original's row of ply 1 (`DG:93B0`, length `[B42B]`), which is built by copying the row of the ply below up to that row's end (`pv_end`, `DG:AAF6 + ply`; `searchnode.zig` `pvUpdate`, 0000:417C / 4D62; at the root 0000:2882–2A30, `[AAF8]`). The rows and their ends are never cleared between searches. Where a move's score is given without the child node being entered, the child's row end is the one the last node entered at that ply left, so the copy can carry moves of another line: of another branch, or, in a game continued from search to search, of an earlier search. That is the cause found [traced: two lines in 117 plies of self-play, `src/engine_options_test.zig`: after 31.Bg3-d6+ the line went on with ...a7-a6, Black being in check; after 53...Kf8-g7 54.Qc8-f5 with a move of a king on f7, the king being on g7]. The path through which the child is not entered is not identified [read, one candidate: `searchnode.zig` `hashMoveFirst` (`30-search-node.md` B9), where the hash move that undoes the side's last move is scored −1 without a search and then copied with `pvUpdate`; not traced]. A rebuilt position (start-up image) shows none, which is why replaying the match's positions afresh found nothing. The search never reads the PV beyond its use by `set_predicted_reply`, which tests its move for legality. **What is sent**: every PV is played move by move on a scratch position from the root (`uci_report.PvCheck`, `src/legality.zig`: the move must be one of the generator the original uses at that ply, `gen_evasions` when the ply's check record is set (at the root the game record's byte, 0000:0693; below it the byte `make_move` writes) and `gen_all_moves` with its cap of 100 otherwise, generated under the build's class C fixes; not castle out of check; not leave the mover's king attacked: with DEV-050 corrected, true perft. Before DEV-066, `gen_all_moves` at every ply, which in check with more than 100 pseudo-legal moves left out the king's moves and cut the line after its first move) and cut before the first move that fails; the same test guards the move handed back (`bestmove`, AGENTS.md §9.3 item 3) and its fallback. Since 2026-11-22 the first move is cut too when it fails (the line is then sent without a `pv`): the search can hand back a root move that is not legal while a legal one exists (`docs/ROBUSTNESS.md`, finding 6), which the guard replaces; before, the first move always stayed. Reporting only: the search's state is read, never written (`np-open-white-d3` gives the same nodes, makes and line hash with reporting off and on). The original's display would show the illegal tail.

**The move played** (AGENTS.md §9.3 item 3, class B). The move handed back is tested in the same way. Seen once in self-play: a program checkmated in a continued game (no legal move) handed back `[A36C]` left from its search before; the engine then prints `info string no move: the game is over in this position (the original's search gave …)` and `bestmove 0000`. Were a move illegal while legal moves exist, the first legal move of the original's root list (`DG:3BC4`) would be played, with an `info string illegal move: …`; that has not been seen. Such a move is not played on the held game: the next position is rebuilt.

## Opening book

The original's opening book (`PRBOOK.M80` and the index `M80KEY.000`–`.00F`, 3,955,910 bytes) is embedded in the executable by the build (`build.zig`, `src/engine_data.zig`; a test checks each file against `reference/CHECKSUMS.txt`). With `OwnBook` on, the engine consults it exactly as the original does in normal play with the shipped settings (`docs/arch/40-opening-book.md`; `src/book.zig`; `EngineRoot.bookProbeFiles`): the **tournament book**, or the book `Book` names, learning and book learning off, no user books; the book is probed at the program's every move while in it and for ten plies after it was left (the gate `4793:6246`), a transposition back into it within those ten plies is found, and a position set up with `position fen` never uses the book (Setup mode sets `DG:70E4`, as in the original). The draw is the original's: `rand() % total` on the C library's generator (seed `DG:2DC8`), repeated in the tournament book until a slot of grade 4 or more, with exactly the original's calls, so a game's book moves depend only on `Seed` and the moves played.

**Reporting.** A book move prints `info depth 1 seldepth 1 nodes 0 nps 0 time … hashfull … pv <move>` (no score: the book gives none) and `info string book move: the original's opening book played <move> without a search`, then `bestmove <move>` with no ponder move.

**Illegal book moves** (AGENTS.md §9.3, class B). The shipped book lists five moves that pass the original's own move check (`4793:59FE`, which does not test check or the squares a castling king crosses) but are not legal. The draw is made as the original makes it (same slots, same `rand()` calls, so every legal outcome has the original's odds); the move drawn is then tested by an independent legality test (`EngineRoot.bookMoveLegal`: the move is one of the generator the original uses there, `gen_all_moves`, or `gen_evasions` in check (DEV-066), it does not leave the mover's king attacked, and a castling move does not start in check or cross an attacked square). If it fails, it is a book miss: it is not played, the book-exit ply is set as when no move is drawn (`6D80`), the engine searches, and `info string book miss: the book drew <move>, which is not legal here (AGENTS.md 9.3): searching` is printed. The move is neither re-drawn nor dropped from the slots.

## Tablebases

**Since 2026-11-21 the engine embeds 66 tablebase files** (owner decision 33; DEV-F21): the installed KPK, KQK and KRK, and, compressed, KBK, KNK and every four-man material except KPPK and KPKP, from the files the owner added (`reference/tablebases/m80-cd/`). At the root of a search with five men or fewer, a position that wins by the tables, or whose every move is scored from them, is played without a search, with its score and `info string tablebase move`. Since 2026-11-22 (owner decision 37) all 60 compressed files are unpacked at `uci`, before `uciok`, on up to 8 threads (`src/tb_store.zig` `preloadAll`, called by `src/uci.zig`): about 0.2 s in ReleaseFast and in ReleaseSafe (1.1 s on one thread), so no `position` or `go` pays for it (`docs/ROBUSTNESS.md`, finding 2). The process then holds them, 228 MiB: private bytes about 312 MB after `uciok` (83 MB before), since the option, true by default, comes after `uciok`. **Since 2026-11-22 (owner decision 44) `setoption name Use Tablebases value false` frees them** and `true` unpacks them again (`TbStore.setUse`, called by `src/engine.zig` `applyOptions`). Both run on the shell's worker, the thread that searches, when it reaches the queued `setoption`: a `setoption` sent during a search waits for that search's end (an infinite or pondering one is ended by it, as by any engine command), so no search reads a file that is being freed; and an `isready` sent after the `setoption` is answered only after it, so after `true` every file is held before the `readyok`. The store's lock keeps the release apart from a `uci` that arrives on the input thread meanwhile. With the option false nothing is unpacked: not at `position` (`prepare`), not by the probe's lookup (which with the box unticked asks only for the empty additional path in any case), not at a second `uci`. Measured (ReleaseFast, `tools/scripts/uci_protocol_test.py` session "tablebase memory follows the option", twice round): 311 MB after `uciok`; 83 MB after `false` and `isready` (7 to 9 ms for the two); 311 MB after `true` and `isready` (130 to 150 ms); then the first five-man position with `go wtime 200 btime 200` answered in 1 ms. The six installed files are the executable's own bytes and are never freed. An engine that never receives `uci` (the test suite's) still unpacks a file when a `position` first makes it reachable (once each, at most about 55 ms a file), not inside the search. `Use Tablebases` (default `true`) covers all 66; `go infinite` does not use them. The paragraphs below were written for the installed six and hold for the 66; the tests with the installed six alone run inside the test suite (`Engine.init`), not in the executable.

The original's KPK, KQK and KRK tablebases (`reference/original/M80/TB`, six files, 425,984 bytes) are embedded in the executable by the build (`build.zig`, `src/engine_data.zig`; a test checks each against `reference/CHECKSUMS.txt`), so the engine needs no data folder. They are bound to the root (`EngineRoot.tb_files`) as the original's `<program>\TB\` folder; the additional path (`5A7B:5038`) is empty, as shipped.

The engine uses them exactly as the original does with its shipped setting, `DG:239C` = 0Ah (`docs/arch/41-tablebases.md`): **at the root of every search with five men or fewer**, each root move is made and probed (`0000:0F8E`); when some root move wins by the tablebase, or every root move was scored from the tablebase or was illegal, the root plays the best-scored move **without a search** (`0000:0FEA`, ties to the first in root-list order, the reverse-move 4/5 rule included); a position with a move that leaves the tablebases (a capture to KK, or a material with no file: with the 66, KPPK, KPKP and every five-man material; with the installed six, also KBK, KNK and every other four-man material) is searched as usual. **The search does not probe** (its callers test `[239C]` ≥ 0Bh). The default is the original's as shipped (`SETTINGS.M80`). The option `Use Tablebases` is the dialog's "Use tablebases" box (above, "Options"); the rest of the dialog ("Dynamic tablebases", an additional path) is not exposed. **An infinite search does not use them** (owner decision 22): `go infinite`, `go ponder infinite` and a `go` with no limit clear bit 3 of `[239C]` for the search and restore it after.

**Option off, and files unbound.** With the box unticked (`[239C]` = 02h) the root's pre-scoring takes the evaluation path at `0000:0F73` without calling the probe. With the files unbound (the engine's tests) the probe is called at `0F87`, fails, leaves `[7466]` and everything else as they were, and the move goes to the same evaluation path (`0F9D`, AX = 0). In the engine the two are the same search: proved equal on move, nodes, makes and line hash on the 14 searches of `tboff.jsonl`'s positions. In the original a failed probe opens files, which the engine does not model; nothing it writes is read by the search [read].

**Proved, tablebases off** (`src/engine_options_test.zig`): the 14 searches of `tests/golden/tboff.jsonl` (the original with "Use tablebases" unticked, `[239C]` = 02h; KRK, KQK, KPK and the promotion race, auto-play) replayed as the oracle played them, with `Use Tablebases` false: all equal on move, node entries, makes and line hash. Through `position fen … moves …` and `go depth N`, with the option false and with the option true and `go infinite depth N`: 13 of 14 equal; the fourth KRK search is the one in which the original kept its hash tables from the search before (the header's `hash_kept`), which a rebuild cannot (above, "The operator script"). After an infinite search the next `go depth 4` plays from the tablebases again.

Proved (`src/engine_test.zig`): the 18 searches of `tests/golden/corpus2.jsonl` scenarios `krk-d4`, `kqk-d4`, `kpk-d4` and `promotion-race-d5`, each as `position fen <scenario> moves <the moves before it>` and `go depth N`, equal to the original on the move, node entries (0 for the 17 tablebase moves), makes and line hash; the same KRK searches without the files differ (the engine searches). `tools/scripts/uci_protocol_test.py`, session "tablebases": KRK moves with `go depth` and a clock, the score `mate 11`, a KPK draw at `cp 0`, the defending side's `mate -N`; since the 66 files (checked 2026-11-22), KQKR played from the files with a mate score, KBK played from them at `cp 0` with no search, and KPPK, which has no file, searched.

## Hash

`Hash` is the original's Settings / Hash-tables dialog (`38C0:4C36`–`4CE6`; `docs/arch/35-hash-sizing.md` §4.2; owner decision 24). `setoption name Hash value N` types N × 1,024 KB there **at once**, as the dialog acts (`src/engine.zig` `setHash`, `src/engine_root.zig` `hashMenuImage`): the request `[12C6]` and the total `[12CA]` become that value, the port of `hash_resize` (`0000:6C3A`) runs, and the main tables are cleared. This is done in the start-up image every game starts from and in the game held, so a change between two moves of a game clears that game's tables, as the dialog does. Before each search main asks for `[12CA]` again (`0000:079F`–`0818`; at the Fixed depth level the 320 KB rule of timed levels never applies), and the resize gives:

| `Hash` (MB) | Total typed (KB) | Each table (KB) | Slots | Mask | 3/4 index |
|---|---|---|---|---|---|
| 1 | 1,024 | 320 | 32,768 | 7FFFh | no |
| 2 | 2,048 | 640 | 65,536 | FFFFh | no |
| 3–4 | 3,072–4,096 | 1,280 | 131,072 | 1FFFFh | no |
| 5–9 | 5,120–9,216 | 2,560 | 262,144 | 3FFFFh | no |
| 10–19 | 10,240–19,456 | 5,120 | 524,288 | 7FFFFh | no |
| 20–29 | 20,480–29,696 | 10,240 | 1,048,576 | FFFFFh | no |
| 30–39 | 30,720–39,936 | 15,360 | 1,572,864 | 1FFFFFh | yes |
| 40–59 | 40,960–60,416 | 20,480 | 2,097,152 | 1FFFFFh | no |
| 60 | 61,440 | 30,720 | 3,145,728 | 3FFFFFh | yes |

The tables stay allocated at the largest size (`engine.table_slots`), as the original's XMS blocks are never reallocated; the mask and mode keep the index within the size in use. The default, 60, types nothing: start-up's total is already 61,440 KB. `info hashfull` is the share of used slots among the first 500 of each table's size in use. The correction of DEV-042 needs nothing at smaller sizes: the original's clear leaves stray bytes only when the size in use equals the block (the full size), and the engine clears every slot.

**Proved** (`src/engine_hash_test.zig`): the 20 auto-play searches of `tests/golden/hash.jsonl` (the original with 1,024, 8,192, 32,768, 49,152 and 61,440 KB typed into the dialog, depth 5) replayed as the oracle played them, the tables carried, and each through `Hash`, `position startpos moves …` and `go depth 5`; and its normal-play game at 1 MB, continued move by move: all equal on move, node entries, makes and line hash, and each header's size, mask and mode equal to the engine's. Each value 1 to 60 gives `src/hashsize.zig` `menu`'s size, mask and mode.

## Engine interface

`src/uci_engine.zig` defines what the search is put behind:

| Call | When | Contract |
|---|---|---|
| `applyOptions(*const Options)` | at start and after each accepted `setoption` | The whole option set. |
| `newGame()` | `ucinewgame` | Followed by `setPosition` of the start position. |
| `setPosition(*const fen.Description, Route, []const UciMove) ?[]const u8` | `position`, after the shell's checks | Null if accepted, else the reason for rejection. |
| `search(*const Limits, *Signals, Output) Result` | `go`, on an accepted position | Blocks until done; reads `Signals.stop`; may print `info` lines through `Output`; returns the move (or null) and an optional ponder move. Never prints `bestmove`. |

All four calls are made on the worker thread, one at a time. `Route` is `new_game` for `startpos` and `setup` for a FEN, because the original searches the same position differently by the route it was reached (`docs/OBSERVATIONS.md`).
